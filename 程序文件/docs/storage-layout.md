# 资料库目录说明

当前只有一个正式资料库：`资料库/items/`。日常使用根目录的 `多平台资料库.exe`；条目按“日期_平台_标题”命名，当前阅读文件使用文章标题。旧文章库归档到 `版本备份/单库整理-20261021/旧文章库/`，不再作为第二个日常资料库。

```text
多平台资料库/
├─ 多平台资料库.exe          日常入口，启动时不需要黑色终端
├─ 启动多平台资料库.cmd      旧启动方式，兼容保留
├─ README.md / CHANGELOG.md   使用与版本说明
├─ 程序文件/
│  ├─ src/                   TypeScript业务逻辑
│  ├─ link-window.ps1        Windows窗口与交互
│  ├─ launcher/              无控制台启动器源码
│  ├─ scripts/               构建、工具安装、维护与核验
│  ├─ tests/                 回归测试
│  ├─ docs/                  操作、架构、计划与验收记录
│  ├─ dist/                  构建后的运行代码
│  └─ tools、模型、依赖、专用浏览器与logs/  本机运行材料
├─ 资料库/
│  ├─ items/                 所有平台的正式资料
│  ├─ staging/               未完成任务与恢复材料
│  ├─ exports/               主动导出的目录包与ZIP
│  ├─ queue.json             采集队列
│  └─ .library-layout.json   目录版本标记，交由程序维护
└─ 版本备份/                 完整恢复ZIP、快速回退与早期迁移备份
```

`src/` 的主要分工：`content-input/acquisition/service`负责链接解析、采集和任务流程；`content-library/naming/paths`负责入库、命名、哈希与引用；`content-render/reading`负责阅读页和当前PDF选择；`content-enrichment`及相关模块负责OCR和转写；`content-jobs/organization/transcript-edit`负责队列、收藏标签、导出与校订；`article-*`和`mcp/`保留微信接口。界面仍使用WinForms，黑色窗口由启动方式决定，无需更换界面框架。

## 单条资料

```text
YYYY-MM-DD_平台_标题/
├─ 文章标题.html             当前离线阅读页，支持媒体播放
├─ 文章标题.pdf              当前PDF；原件模式不会强制生成
├─ 文章标题.md               整篇正文；视频等资料包含已取得的文字稿
├─ 图片/001.png、002.jpg等    原图，保留实际格式和字节
├─ 视频、音频、封面等/       按类型保存的原件；有内容才生成子目录
├─ 处理结果/
│  └─ 图片文字、文字稿、截图等/  辅助OCR/ASR及其人工校订稿
├─ 历史版本/
│  ├─ 阅读/                  已替换的阅读文件
│  ├─ 清单/                  有意义的旧清单及迁移前审计清单
│  └─ 原件/                  后续采集改变原件时，先保全旧字节
├─ .内部/
│  ├─ 采集记录/              微信原始页面、采集正文、采集清单原样留存
│  └─ 其他程序记录           原始识别JSON、非文章的原始正文等
├─ content.json              正式索引和资产哈希，程序维护
└─ manifest.json             微信接口兼容索引，仅微信条目有
```

日期取已有采集时间（北京时间），同名目录用`(2)`等序号区分；稳定ID保存在清单中。取消原始资料外壳和两份当前文章正文，日常只需看同名HTML/PDF/Markdown与图片。静态图片及其OCR按三位序号排列，视频帧仍保留有意义的时间点。机器原稿、人工校订及其历史继续保留。

界面“打开阅读页”“打开PDF”“打开文字稿”分别指向同一条目的这三个文件，“打开目录”打开该条目目录；“打开来源”打开原链接。“打开文字稿”读取整篇正文，文章不再混入图片OCR；“管理资料 → 校订识别稿 / 转写稿”单独编辑识别稿。“导出”提供资料目录包和ZIP，包含当前阅读文件及本地资源；标签、收藏、结果详情与补缺项归入“管理资料”。

公众号条目有已保存的原始页面时，当前阅读页直接保留原文的正文顺序、图文位置和安全的内联排版，图片替换为本地文件；PDF从同一阅读页生成。OCR与转写仍用于搜索和校订，通过阅读页折叠附件或窗口按钮访问，不重复插入原文PDF。采集状态和机器字段不作为原文打印。没有原始页面的旧条目继续使用通用阅读页；原始快照本身不执行，也不改写。

原先的`阅读.pdf`和`阅读 (2).pdf`是不同的生成版本。当前版本改为标题文件名，旧文件保留在历史与整理前备份中。公众号PDF从保留原文图文顺序的阅读页生成，图片OCR作为辅助材料，不重复插入原文。

## 当前兼容、备份与回退

新旧微信接口均解析到正式资料库；同项目原`文章库`显式路径在新进程中也会解析到正式库。旧文章ID继续可查，自定义独立库路径不被强制改写。已经加载旧代码的MCP服务需要重启，窗口需要重新打开；不会强制关闭其他会话的进程。

`版本备份/单库整理-20261021/`保存本次整理前的`整理前完整资料.zip`（870文件，1,515,500,468字节）和`整理前源码.zip`（300文件，2,949,081字节），均逐文件回读SHA-256通过。`旧正式条目/`及`旧文章库/`是快速恢复原目录，`单库整理日志.json`记录新旧路径和完整目录签名。

维护命令在`程序文件/`内运行：`node --import tsx scripts/consolidate-library.ts <项目绝对目录> <本次备份绝对目录> verify`核对整理结果；`rollback`在全部目录签名和目标位置均通过预检后回退。资料整理后有任何修改或新增占位时拒绝覆盖。日常使用不运行迁移或回退；完整ZIP支持在隔离目录恢复核对。

本次只整理已存在的18条资料。历史失败的“动态-哔哩哔哩”条目原本未取得正文，整理保留其状态与证据，不把空内容视为已经恢复全文。未知staging、队列、标签收藏、校订、账号、模型与依赖均保留。

## 历史：2026-10-16存储统一

当时为已运行的旧代码保留了隔离兼容目录；图片不做硬链接，避免原地改写污染正式库。核验相同字节的PDF和视频共享存储，19份副本共享77,498,177字节。该兼容目录本次整体归入版本备份，以上数字是历史记录。

普通处理中间保存不再逐步堆积历史清单。现有101份历史快照中，只移除了同一次采集、原件和派生字节均已被当前版本覆盖的80份中间快照；保留21份原有快照及17份迁移前审计清单。用户校订历史不参与此清理。

未知staging仍需保留，它们可能用于失败恢复或保全未正式入库的内容。依赖、模型、专用登录资料和Git历史有各自用途，本轮未按体积清除。

`版本备份/存储优化-20261016-084810/`包含：

- `备份核验.json`、`收尾前备份复验.json`：完整清单和核验结果。

本轮演练目录和迁移准备区已经核验清除。完整ZIP与快速回退材料有不同恢复用途，仍保留。

## 后续维护时复用

本节是项目存储维护细则的主位置，供下一次新增布局、去重或回退功能时使用；日常阅读和小范围文字更新不运行迁移。

- 共享文件前检查全部仍可能运行的写入方。旧代码会原地写图片时，保持隔离副本；不能只凭相同哈希就做硬链接。使用“临时文件加替换”或拒绝覆盖的格式，也须先核对实际实现和字节。
- 改目录要同时更新清单、Markdown、HTML、当前PDF、导出和恢复路径。路径映射覆盖本轮保全的所有文件，包括只被历史快照引用、已退出当前资产列表的旧文件。
- 回退先完整预检，再按目录实际状态和签名协调日志中断点。重复回退不删除已恢复文件；发现迁移后的新增或修改就保留双方，拒绝覆盖。
- 项目整体改名后，相对阅读引用仍可用；旧迁移日志中的绝对项目及备份路径仍是当时的证据，工具会拒绝不一致的目标。保留原日志，不批量替换历史路径；需要恢复时先用完整ZIP在隔离目录核对，再由维护流程处理迁移位置。

这些结论已由本项目代码、回归及上述正式验收承接。通用的备份、恢复预检和消费者检查沿用现有变更恢复方法，不另建用户级规则或Skill；跨项目效果待下一次真实同类任务验证。
